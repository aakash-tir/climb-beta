## Expanded the plan and scaffolded climb-beta

**What we did:** Turned the one-paragraph brief into a full `plan.md` (scope, exit
criteria, a stack table with rejected options, architecture, milestones M0–M8), wrote
four research notes in `docs/research/`, and scaffolded the repo: the uv project
(Python 3.11, core deps only by default, plus `ml`/`data`/`label`/`app` extras), the
`climb_beta` package with config loading and the shared `Detection` type, the first
tests, a PR-only path-filtered CI workflow, PR and issue templates, the `.claude/`
rules (git workflow, issues → PRs → green CI, lean CI, in-PR graph/diagram refresh), and
the graphify wiring.

**The reason:** The brief fixed the design (a colour-blind YOLO11-seg detector, then a
separate colour step) and the exit criteria, but left open where the data lives, how the
public dataset's labels look, how labelling runs, and how CI stays fast with a
torch-heavy project. The owner answered three questions: the repo is **public**, the
Basecamp photos stay **out of git** (local plus a private HF dataset), and the Roboflow
converter takes **polygons if present, otherwise SAM masks from boxes**.

**How it was solved:**
- **CI never installs torch.** Everything the tests touch (colour rules, route grouping,
  conversion, wall split, metrics) is numpy + OpenCV. Heavy imports are lazy, and
  `@pytest.mark.ml` tests are skipped by default. This keeps a CI run to about a minute.
- **The torch index is cu128**, because the training laptop's RTX 5070 Ti is Blackwell
  (sm_120), and older CUDA wheels don't support it.
- **Roboflow couldn't be verified by script** (Universe returns 403). One project with
  the brief's dataset name is box-only, so the converter handles both cases. Pinning the
  exact project is a `needs-decision` issue (#12).
- **Public-repo hygiene:** `graphify claude install` wrote an absolute home-directory
  path into `.claude/settings.json`. It was replaced with the bare `graphify` command.
  `graphify-out/cache/` embeds absolute paths in node IDs, so it's gitignored (the main
  graph files were checked and don't contain them). Git uses the GitHub noreply address
  for this repo.
- No architecture diagram yet: there's no runtime structure to draw until the colour
  and route modules land (#25).

## Synthetic hold images for tests (#1)

**What we did:** Added `tests/synth.py`: a textured near-neutral wall, elliptical holds
in a given BGR colour with brightness-only edge shading, chalk applied centre-first or
scattered, and coloured-light tint. Reference hold colours (red, hot/light pink, …)
live there too.

**The reason:** The colour and route rules need repeatable inputs that reproduce the
real failure modes (chalk on the grip surface, warm light) long before any Basecamp
photo is labelled.

**How it was solved:** Centre-first chalk mimics where hands actually go, so a hold's
edge ring keeps its pigment. The white-hold rule (#6) depends on exactly that.
Shading changes only brightness, never hue, so a test can't pass by accident through
a hue shift. Test-only code, so no diagram change.

## Add mask utilities (#2)

**What we did:** Added `climb_beta.masks`: erode/dilate (elliptical kernel, image border counts as outside), `edge_ring`, `mask_iou`, `iou_matrix` (skips pairs whose boxes don't overlap), `distance_to`/`min_gap` (distance transform), polygon ↔ mask, and YOLO (de)normalisation.

**The reason:** The white-hold rule needs the inner edge ring, route grouping needs mask-to-mask gaps, eval needs IoU matrices, and the converters need polygon/mask round-trips. One tested home avoids four slightly different copies.

**How it was solved:** `edge_ring` treats the image border as boundary, so a hold cut off by the frame still has a ring on that side. `min_gap` uses a distance transform of one mask evaluated on the other's pixels, and accepts a precomputed transform so route grouping can reuse it across pairs. No diagram change (utility module).

## Add grey-world white balance with wall reference (#3)

**What we did:** Added `climb_beta.colour.white_balance`: `grey_world_gains(img, ref_mask)`, `apply_gains`, `grey_world`. Gains come from the reference pixels (the wall, when a mask is given), ignore clipped highlights, fall back to the whole image when the reference is tiny, and are clipped to [0.5, 2].

**The reason:** Gym LEDs tint everything warm, and that shifts every hold's hue and saturation before the colour rules see it. A plain whole-image grey-world is biased by the holds themselves, since they're deliberately saturated and often mostly warm colours.

**How it was solved:** The test that matters crowds a wall with red/orange/yellow holds under a warm tint. Wall-referenced gains bring the wall to within 4 levels of neutral and beat whole-image gains on it. Highlights at 250+ are excluded because a clipped channel says nothing about the light. No diagram change (the diagram lands with #25).

## Add chalk-aware per-pixel colour family voting (#4)

**What we did:** Added `climb_beta.colour.rules`: `hold_pixels` (HSV + Lab inside the mask, chalk flag), `pixel_labels` (black / white / grey / hue family per pixel), and `classify_hold` / `classify_pixels`, which vote over non-chalk pixels and return a `ColourResult` with name, confidence, votes, chalk fraction and a reason. Families resolve to colours through a `FAMILY_RESOLVERS` hook that #5 (pink/red) plugs into. Synthetic yellow was moved to a truer yellow (hue ≈ 52°).

**The reason:** This is the core of the rule-based colour step. Chalk is the main failure mode, because averaging chalked pixels washes any colour out, so chalk pixels get no vote at all.

**How it was solved:** Labels are assigned in priority order: hue family, then achromatic (S < 60) as white/grey by V, then black (V < 70) overrides everything, since hue is meaningless in shadow. Tests: seven plain colours, blue chalked 30/60/80% centre-first, scattered chalk on green, and a sweep of the whole hue circle with no gaps. A fully chalked hold returns `unknown` until the white edge-ring rule (#6) lands. No diagram change.
