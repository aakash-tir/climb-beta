## Registered the first four Basecamp walls (#78)

**What we did:** Took in the first batch of Basecamp phone photos (9 iPhone HEIC files),
converted them to JPG, and sorted the 8 wall photos into `data/basecamp/raw/wall-01` …
`wall-04` (gitignored, private). Added the four walls to the committed
`data/basecamp/walls.yaml`, all `angle: vertical` for now, per the owner. The ninth photo
is the gym's "Boulder Circuits" sign, kept out of the dataset as reference.

**The reason:** The split script needs the walls registered before any labelling or
splitting, and photos must be grouped by wall so a route can never land in two splits.

**How it was solved:** The owner described which photos show the same wall and which
routes run across photos. Adjacent sections that share a route got one wall id (wall-02
covers three photos). HEIC → JPG conversion used a one-off `pillow-heif` run, applying
the EXIF rotation and then dropping all EXIF metadata (including GPS); every output file
was checked to have 0 tags. The originals sit in `raw/.incoming/`, because the split
script skips dot-folders and would otherwise have counted the folder as a wall. The
owner's per-route notes are in the gitignored `data/basecamp/labels/route_notes.yaml`,
to become `routes.yaml` ground truth after labelling. `splits.yaml` isn't assigned yet:
four walls is too few for a useful train/val/test split.

**Follow-ups filed:** The owner's description of how Basecamp marks routes doesn't
match the route step. A route is hold colour **plus** the colour of small tape diamonds
(the grade circuit). Two diamonds at the bottom mark the start, one at the top marks the
finish, and only routes with both count. Grey and black holds can be used on any climb.
Filed #79 (tape colour as grade), #80 (start/finish from diamonds), #81 (group by hold +
grade), #82 (shared grey/black holds, `needs-decision`), #83 (exit criterion on complete
routes).

Data metadata only, no architecture change: no diagram update.

## Colour tape diamonds as the route grade (#79)

**What we did:** The colour step now labels `tape` detections as well as holds. Which
classes are coloured is a new `coloured_classes` list in `configs/colours.yaml`
(`[hold, tape]`; it defaults to `[hold]` when the key is missing).

**The reason:** The owner explained that at Basecamp a route's grade is shown by small
tape diamonds, and the diamond colour (the grade circuit: yellow, orange, red, green,
purple, pink, black, white) is separate from the hold colour. Two routes on one wall
can share a hold colour and differ only by diamond colour. The route step can only
tell them apart if tape detections carry a colour.

**How it was solved:** `colour_detections` colours every detection whose class is in
`coloured_classes`, with the same rules and thresholds as holds. That made sense
because the diamonds use the same palette. Synthetic tests draw a small diamond in
each of the eight circuit colours next to a hold, and all eight come out right,
including white, which goes through the white-ring rule. Volumes stay uncoloured. The
rules CLI test now expects the white tape in its scene to be labelled `white`. The
crop classifier still only relabels holds; colouring tape with it is out of scope.

No new component or flow: tape detections now also carry the existing `colour` field,
so no diagram update. The diagram will be redrawn when routes gain a grade and a finish
(#80, #81).

## Mark start and finish holds from diamond tape (#80)

**What we did:** Routes now have a `finish` hold and a `complete` flag as well as
`starts`. The pipeline JSON reports both, the overlay marks the finish "F", and the
demo text says when a route is incomplete. `named_route()` now prefers the largest
complete route. The architecture diagram's colour and route boxes were relabelled.

**The reason:** The route step treated every tape-touched hold as a start and had no
finish. At Basecamp two diamonds at the bottom mark the start, one diamond at the top
marks the finish, and the owner counts a route only when both are visible. Several
routes in the first photo batch are visible only in part (start only, or finish only).

**How it was solved:** Each hold now counts how many tape pieces touch its grown mask,
using the existing reach. Within a route, the highest taped hold is the finish if it has
exactly one diamond and its centre is in the top `finish_top_frac` (0.5, in
`configs/route.yaml`) of the route's height. Every other taped hold is a start, which
covers two-hand starts with one diamond per hold. Using a position rule as well as the
diamond count stops a single diamond low on the wall, such as half a start pair, from
being read as a finish. Synthetic tests cover complete, start-only, finish-only,
two-hand starts, and a pair of diamonds at the top. Known limit: if the detector
merges two touching diamonds into one tape mask, they count as one.

Diagram updated: the route box now reads "2 diamonds = start / 1 diamond at top =
finish", and the colour box reads "Colour hold + tape" (catching up with #79). The
render was checked with a headless-Chrome screenshot.
